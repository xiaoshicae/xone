# 更新日志

本文件记录 XOne 的版本变更。版本号遵循[语义化版本](https://semver.org/lang/zh-CN/)，
标记 `!` 或 `BREAKING` 的条目包含不兼容变更，升级前请阅读。

- **v2.35.0** (2026-09-15) - perf(xgin/xlog): the three highest-impact findings from the middleware hot-path analysis. The Log middleware accounted for 86% of everything the default five-middleware chain adds per request, so all three are about it. First and largest: everything the middleware does — the body snapshot, wrapping the ResponseWriter to capture the response, the redaction and serialization after the handler returns — exists only to produce one access-log line, but xlog.Info checks the level inside itself while requestInfo is built as its argument, so a service running at warn level paid the whole cost and threw the result away. A new xlog.Enabled lets the middleware check first: measured with mockey, the disabled path drops from 21243ns to 10102ns against a 7994ns baseline. Second, bodyMayContainSensitiveField called bytes.ToLower on the whole body to do one case-insensitive comparison, allocating a full copy of every request body; it now scans once against a 256-entry first-byte bitmap and only folds where a field name could start, which is allocation-free — a 64KB body goes from 337780ns/711420B to 281262ns/637233B. The replacement was differential-tested against the old implementation over 2023 inputs including 2000 random mixed-case strings, because a miss here means a plaintext password in the logs. Third, RawLog added record attributes one call at a time, and slog.Record inlines only five before it starts growing its backing slice — slices.Grow was 14% of all bytes allocated in the profile; attributes are now collected into a stack array and handed over in one call, which leaves the common two-or-three-field log at exactly its previous cost (a plain make would have added a heap allocation to every such call) and takes the eleven-field access log down by 3 allocations. Net on the full chain: 30558ns/15130B/131 allocs to 28843ns/14761B/128. Single-request latency for a small body is unchanged; the wins are in allocation count, large bodies, and the disabled-level path. Also fixes the benchmark added in v2.34.2, whose handler never read the request body, so the redaction path it was meant to measure never ran; and the level-disabled case now skips itself rather than silently reporting the enabled number when run without -gcflags="all=-N -l", which mockey requires
- **v2.34.2** (2026-09-15) - test(xgin): add benchmarks for the middleware chain, which had none. Each runs a full gin request so the number is "what this middleware costs per request" rather than what one function costs in isolation, and a no-middleware baseline makes the subtraction meaningful. What they show: Recover is free (+0ns, +0 allocs), LogScope +322ns, Metric +429ns, Trace +1006ns against a noop tracer — and Log +21635ns with 76 extra allocations, which is 86% of everything the default five-middleware chain adds. A separate case mocks xlog.Info to a no-op to measure what the Log middleware pays before the level check is reached, since requestInfo is built as an argument to Info while the check lives inside it; a large-body case separates the cost that scales with request size from the fixed cost. No production code changes — this is the regression floor the module was missing

- **v2.34.0** (2026-09-15) - change(xgin)!: the default port becomes 8080, matching gin's own. gin's resolveAddress returns ":8080" when no address is given, so a service that dropped xgin in front of a plain gin router silently moved to a different port, and every getting-started snippet, container port mapping and health check written against gin's default needed a correction that nothing announced. 8000 was never chosen for a reason the code records. Only the default changes: XGin.Port set explicitly in YAML behaves exactly as before (BREAKING: a service relying on the default port now listens on 8080 — set XGin.Port: 8000 to keep the old one, and check container port mappings, health checks and ingress rules that hardcode it)
- **v2.33.0** (2026-09-15) - feat(xlog/xgin)!: make the request-scoped KV bag actually work, which is what the Session middleware always claimed to do. Its comment promised a log context container initialized at the start of the request and carried through the whole request, but CtxWithKV is copy-on-write: every call builds a new map and returns a new context, and KVFromCtx hands back a copy. Two consequences, both measured. The middleware was a no-op — seeding an empty map changed nothing, because CtxWithKV creates a container itself when the context has none, so a request behaved identically with and without it. And the capability it advertised did not exist: a handler writing ctx = xlog.CtxWithKV(ctx, kv), the natural spelling, produced a context nobody else saw, so the access log that the Log middleware writes after c.Next() got nothing — and a business function deep in the call stack cannot fix that, since it has no *gin.Context to write back to. The container is now a pointer to a locked map, so writes are visible to every holder of the context: CtxWithKVScope opens a scope (idempotent, so re-registering the middleware cannot wipe fields already written), and AddKV/AddKVs write in place and return nothing, because returning a new context is precisely what a deep call site cannot use. CtxWithKV keeps its exact previous semantics — it now derives a new scope seeded from the parent's snapshot, so the caller's context is still unaffected — and the two are documented as a choice of write direction: AddKV for request-level fields the access log should carry, CtxWithKV to tag one stretch of a call chain without touching the rest. Calling AddKV with no scope open drops the write and logs it under debug, since "the field just is not in the logs" otherwise leaves no trace. The logging hot path reads the map under a read lock via an internal range helper rather than KVFromCtx, so no copy is made per line: allocations are unchanged at 13/5/19/1 across the four benchmarks and the ns deltas sit inside run-to-run variance. The middleware is also renamed from Session to LogScope: it has nothing to do with HTTP sessions, cookies or login state, and the old name said so to every reader — its four siblings in the package (Trace, Log, Metric, Recover) each say in one word what they do, and now this one does too. Also replaces the session middleware test that gave false confidence — it asserted on a context the handler had reassigned locally, which passed with or without the middleware (BREAKING: xgin/middleware.Session is renamed to LogScope; XGin users register it automatically and are unaffected)
- **v2.32.0** (2026-09-13) - refactor(xgorm/xredis/xcache/xgin)!: stop handing back a nil client, and remove the wrong way to start a server. C returned nil with an error log when no client was configured, but nil is never usable: measured, every method on a nil *gorm.DB and a nil *redis.Client is a plain nil-pointer dereference, so returning it does not let the program get any further — it only defers the same panic to whatever line first uses the client, where the stack says "invalid memory address" and nothing about a missing config. All three now panic at C itself, naming both the client asked for and the ones actually configured ("no client found for name=[typo], configured=[primary replica]"), which separates a misspelled name from an unconfigured module — two different problems that the old single nil collapsed together. This is a startup-time configuration error, not a runtime condition to handle, so each module also gains Has() for the optional-dependency case: use it when configured, skip when not, without going through C to find out. xcache's C keeps a distinction worth knowing: the package-level Get and Set operate on the global cache and lazily create a default instance when XCache is absent, so they never panic; C asks for a named instance that the config was supposed to declare. Separately, XGin.Run and Stop are no longer methods on XGin. The previous release made Run refuse to start without initialization, which turned a silent half-configured server into a clear error but left the wrong door standing next to the right one; now the xserver.Server implementation lives on an unexported ginServer and Start is the only public way in, so skipping BeforeStart is not one method call away. The guard stays behind it as a precondition assertion for future call paths, at the cost of one atomic load (BREAKING: xgorm.C/CWithCtx, xredis.C and xcache.C panic instead of returning nil — use Has() where nil was being checked; XGin no longer has public Run/Stop methods and no longer satisfies xserver.Server, so xserver.Run(gx) must become gx.Start())
- **v2.31.0** (2026-09-13) - refactor!: a review pass over the whole public API for the defect the last release fixed in one place — a name or a return value that promises something other than what the code does. The worst case was not a name at all: XGin.Start and Run are English synonyms with entirely different jobs, Start running the full lifecycle while Run is only the xserver.Server implementation and runs no hooks itself. Calling Run directly failed silently rather than loudly, because an uninitialized xconfig does not report an error — it hands back an empty config, measured: UnmarshalConfig returns nil and the struct comes back zeroed. So the server started on the default port with logging, tracing and every database client unconfigured, and the only diagnostic was a warning suppressed unless XONE_ENABLE_DEBUG was set — the same silent fallback to a port nobody expected that v2.25.0 fixed for config parse errors, still reachable through the other door. xhook gains BeforeStartInvoked and Run now refuses to listen without it. Next worst: xtrace.EnableTrace and EnableForwardHeader read as imperatives but are predicates, and since Go lets a return value be discarded, xtrace.EnableTrace() on a line by itself compiles, passes vet, and does nothing — a way to believe tracing is on when it is off. They become TraceEnabled and ForwardHeaderEnabled. xcache's four Set functions returned an undocumented bool that answers "was it accepted", not "is it cached": ristretto's own doc notes the admission policy may still drop an accepted write, a Get immediately after can still miss because writes are buffered, and at package level false additionally covers a cache that does not exist — all four are now documented in full at both levels. The rest are duplicates and inconsistencies that make names unguessable: xlog.XLogLevel was CurrentLevel().String() under a stuttering name and is removed; xserver.R, a single letter for the one function in its package that does not start a server, becomes Init; four of the five middlewares carried a GinX prefix that repeats both the package name and its parent path, so GinXTraceMiddleware and its siblings become Trace, Log, Metric, Session and Recover; options.WithSwaggerUrlPrefix was the only option in its package with a With prefix, and the drift had already happened — the architecture rules documented options.SwaggerUrlPrefix, which did not exist until now; xhook.MustInvokeSuccess(success bool) read as a statement about the past and becomes MustSucceed(must bool). Finally xmetric.Timer's returned function becomes idempotent, matching TrackInFlight beside it — identical signature, identical usage, and one of them silently double-counting is only a memory burden (BREAKING: xtrace.EnableTrace/EnableForwardHeader, xlog.XLogLevel, xserver.R, xgin/middleware's five constructors, options.WithSwaggerUrlPrefix and xhook.MustInvokeSuccess are all renamed or removed; XGin.Run now returns an error when called before BeforeStart hooks have run)
- **v2.30.0** (2026-09-13) - refactor(xutil)!: rename Go to AsyncWithPool, add TryAsyncWithPool. Go was the worst name in the package because it meant the opposite of what it read as: it shares a spelling with the language keyword, so it reads as "start a goroutine", while it is the one function of the two that starts no goroutine at all — it reuses a pool worker. Async and Go sitting side by side also gave no hint which of them was the pooled one, and xutil.Go(pool, fn) does not parse as a phrase. AsyncWithPool follows the convention the repository already established in CWithCtx, RWithCtx, RetryWithContext, SetWithTTL and GetWithTimeout: XxxWithYyy is the Yyy-flavored version of Xxx, so the reader can see at a glance that the only difference from Async is the pool. Async keeps its name, being the plain form. Its doc comment now also states that the pooled version blocks the caller when the queue is full, which it always did and never said — the same omission that made the package-level Submit a trap. TryAsyncWithPool is added for callers who would rather degrade than wait: it completes immediately with ErrPoolFull, a new error distinguished from ErrPoolClosed because one is transient and worth retrying while the other is permanent (BREAKING: xutil.Go is renamed to xutil.AsyncWithPool; it is a pure rename, the behavior is unchanged)
- **v2.29.0** (2026-09-13) - fix(xutil)!: the pool blocked in two ways users could not see coming. Submit held the read lock while blocking on a full queue, so one stuck task was enough to hang shutdown forever: Shutdown could never take the write lock, and because Go prefers waiting writers, every later Submit in the process then blocked on the read lock too — a task that was only ever meant to fire and forget. Pool gains a done channel, the same shape xlog.asyncWriter already used for exactly this reason: Shutdown closes it first, a Submit waiting on a full queue wakes and returns false, and the write lock is then free. Atomicity is unchanged — a Submit returning true still sends inside the read lock, so the queue cannot already be closed. The package-level Submit is removed rather than repurposed. Its signature promised what it did not deliver: a bool return on a fire-and-forget helper reads as "returns false if it could not be queued", while it actually blocked, and the README said only "返回是否提交成功". Renaming it to TrySubmit makes every existing call site fail to compile, so the semantics change is a decision someone makes rather than one that lands silently. Blocking backpressure is also simply wrong on the global pool: it is shared by the whole process, so one caller filling the queue propagates the wait to an unrelated caller that has no idea it exists and nothing to slow down — it only wanted to record a metric. Pool.Submit keeps blocking, which is right for a pool the caller owns and sized, and Pool.TrySubmit is added for callers who would rather not wait (BREAKING: xutil.Submit is gone — use xutil.TrySubmit for the global pool, or NewPool plus pool.Submit when backpressure is actually wanted)

- **v2.26.0** (2026-09-13) - fix(xgorm/xredis/xcache/xhttp/xlog)!: five silent failures across the service and logging layers. xgorm printed database passwords into the startup log in four common cases: its DSN sanitizer decided the format by whether the string contained an @, so a key=value DSN carrying a routine application_name=svc@cluster took the URL branch, found no colon before the @, and returned the whole string — password and all — unchanged; a password containing @ left its tail exposed; password='my secret' was cut at the quoted space; and a second password= was never masked at all. The sanitizer now dispatches on the actual format, parses URLs with net/url rather than hunting for colons, and walks key=value pairs honoring libpq quoting, masking every credential-bearing key. xgorm also leaked one goroutine per failed connection — none of the four error paths in newClient closed the pool gorm had already opened, including gorm.Open's own automatic-ping failure, measured at exactly one leaked database/sql connectionOpener per attempt. xcache rebuilt its lazily-initialized global cache after shutdown, and nothing would ever close the replacement: a user BeforeStop hook reading the cache is enough to trigger it, since those run after xcache under the same default Order. xhttp handed out clients with no timeout at all before startup and after shutdown — resty.New() and http.DefaultClient both default to zero, meaning never — so a request from a BeforeStop hook could hang the whole shutdown; both fall back to a 30s-bounded client now. And xlog stopped writing entirely after a failed rotation: Write returned the error while still holding a perfectly usable handle on the previous file, and since the async writer keeps only the first error and surfaces it only at Close, the symptom was logs ending one day with nothing reported. It now degrades to the current file and warns at a bounded rate. Also: xgorm and xredis roll back initMulti by removing clients from the map rather than only closing them, so C() cannot return a closed client; both size the ping timeout from dial plus read rather than dial alone, and retry through RetryWithContext so a shutdown signal during startup is not stuck behind attempts×interval; xhttp restricts retries to idempotent methods by default, since a transport timeout cannot distinguish a request that never arrived from one whose response was lost and resending a POST means a duplicate order; xcache warns on a type-assertion miss, which was otherwise indistinguishable from a cache miss; xlog bounds its close-time drain at 5s and falls back to context.Background rather than dropping a log line passed a nil ctx (BREAKING: XGorm.MaxIdleConns becomes *int so an explicit 0 means no idle connections instead of being overwritten by MaxOpenConns; XHttp gains RetryOnlyIdempotent, default true, so POST and PATCH are no longer retried unless it is turned off)
- **v2.25.0** (2026-09-13) - fix(xgin/xserver): three failure paths that ran silently. A handler panic left no trace in either the access log or http_requests_total: the recover middleware was registered outside log and metric, so a panic unwound past both before being caught and neither ran the code after its c.Next() — the 500s most worth alerting on were the only ones missing from the error-rate metric. Recover moves to the innermost position among the framework middlewares and both record through defer, so even a panicking custom RecoveryFunc cannot make a request vanish; process safety never depended on the old order, since net/http recovers per connection anyway. When a BeforeStart hook failed, xserver returned without running any BeforeStop hook, leaving every module that had already initialized unclosed — the log writer never flushed, which is to say the line explaining why startup failed could be the one that never reached disk. And Server.Stop() ran only on the signal path, so a Run() that returned on its own — port already in use, a deliberate exit, a panic — skipped the caller cleanup the Server interface documents as belonging there; Stop now runs on both paths, guarded by a Once. Build() took no lock while registering middleware, so concurrent Engine() calls raced and could register the same middleware twice, doubling every log line and metric increment for the process's whole life; trans read its translator without the lock its writer held. The http.Server was built with no timeouts at all, meaning no timeout rather than a default one, so a slow client could hold a connection indefinitely: XGin gains ReadHeaderTimeout (10s) and IdleTimeout (60s), with ReadTimeout and WriteTimeout left unlimited by default because capping them breaks uploads and SSE, plus a configurable GracefulStopTimeout defaulting to 25s — below the 30s K8s grace period it previously matched exactly. Starting up now fails on a config parse error instead of quietly falling back to port 8000, Stop() before Run() keeps the server from starting afterward rather than leaving it running until the exit wait expires, and a second Run() reports the conflict instead of orphaning the first server
- **v2.24.0** (2026-09-13) - refactor(xmetric)!: put every duration metric on seconds, so the framework no longer contradicts its own advice. v2.23.0 added ObserveDuration precisely because HistogramObserve's second-based buckets made millisecond values useless, yet the two metrics the framework itself exports, http_request_duration_ms and http_client_request_duration_ms, were still milliseconds — a service scraping both got one histogram in seconds and one in milliseconds with no way to tell from the name which was which, and Prometheus' own convention is base units. They become http_request_duration_seconds and http_client_request_duration_seconds, and XMetric.HttpDurationBuckets defaults drop by a factor of 1000. The conversion also fixes a real loss of precision: the inbound middleware and RecordHTTPClientMetric took a float64 of milliseconds produced by Duration.Milliseconds(), which truncates, so every request faster than 1ms was recorded as exactly 0 and the first three buckets were unreachable; RecordHTTPClientMetric now takes a time.Duration and converts once, at the histogram. Add TrackInFlight, which increments a gauge and returns the decrement as a function: GaugeInc and GaugeDec have to be paired by hand across early returns and panic paths, and a single missed Dec leaves the gauge permanently high with nothing to indicate it, whereas defer TrackInFlight(name)() cannot be unpaired and the returned function is idempotent (BREAKING: both HTTP duration metrics are renamed and now report seconds — existing Grafana dashboards, recording rules and alert thresholds built on the _ms names must be updated; HttpDurationBuckets values configured in YAML must be divided by 1000; RecordHTTPClientMetric takes a time.Duration instead of a float64 of milliseconds)
- **v2.23.0** (2026-09-13) - fix(xutil)!: the concurrency primitives in the base layer could take the process down three ways. Submitting to a pool while another goroutine shut it down panicked with "send on closed channel" — the close landed between Submit's context check and its send, and a send on a closed channel is ready in a select rather than skipped; sending and closing are now mutually exclusive under an RWMutex, and Submit reports whether the task was accepted. A panic inside Async, Go or any submitted task killed the process and the worker with it, while xflow, xhook, xlog and xmetric all isolate theirs; panics now become errors on the Future, or a log line for fire-and-forget tasks. And Go on a closed pool returned a Future whose channel was never closed, so every Get on it blocked forever — it completes with ErrPoolClosed instead. The default pool is now created on first use: importing xutil, which every module does, started 100 worker goroutines in every service whether or not it ever submitted anything. RetryWithBackoff doubled its delay before clamping it, so an int64 nanosecond overflow after about twenty doublings turned it negative and disabled backoff entirely; add RetryWithContext and RetryWithBackoffContext so an initialization retry cannot hold shutdown for attempts×sleep. Also stop matching an argument's value as if it were a key in GetConfigFromArgs, and replace the last fmt.Errorf calls with xerror (BREAKING: Submit returns bool; Future gains GetWithContext)

GetConfig and GetHttpDurationBuckets handed out the module's own config pointer and backing array, so any caller could corrupt global state by writing to what it received, and now return copies. Re-initialization panicked outright on MustRegister for the Go and process collectors, and when it did not, the collector cache and the outbound-HTTP sync.Once kept the first Namespace and buckets forever; registration is safe now and closing clears the cache. Add ObserveDuration and Timer, which take a time.Duration and settle both the type and the unit: HistogramObserve defaults to second-based buckets while the HTTP metrics are milliseconds, so timing values passed as milliseconds landed entirely in the +Inf bucket and quantiles were quietly useless. Also fold the three near-identical getOrCreate functions into one generic, log rather than swallow a rejected exemplar, and give the README a decision table, naming conventions and the unit warning

Every processor method had to repeat *xflow.FlowData[OrderReq, OrderResp]; one type parameter holding the caller's own struct leaves only business types in those signatures, and deletes FlowData, Key, NewKey, SetExtra and GetExtra along with their runtime type assertions — intermediate data is now a plain field, checked at compile time.
